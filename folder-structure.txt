Thungatha — Folder Structure and Naming Standard
Status: Proposed target structure; current implementation is not yet fully migrated
Last reviewed: 18 October 2026
Branch: dev

PURPOSE

This document describes what each important folder is for, which filenames Next.js requires, and the intended organisation of production code and tests. It is a target map, not a claim that every folder shown already exists.

NEXT.JS RULES THAT AFFECT THIS STRUCTURE

- Next.js App Router uses filesystem conventions. Keep framework entry-point filenames such as page.tsx, layout.tsx, route.ts, loading.tsx, error.tsx, global-error.tsx, and not-found.tsx where those roles apply.
- Normal folders under src/app/ contribute to URL paths. Do not rename a route folder without considering the public URL it creates.
- Route groups use parentheses, for example (authentication). The group name is omitted from the URL, so src/app/(authentication)/sign-in/[[...sign-in]]/page.tsx still serves /sign-in.
- Route groups are organisational only. Do not create duplicate routes that resolve to the same URL.
- Next.js does not require a particular folder architecture for ordinary modules, components, styles, or tests. Use descriptive names that communicate responsibility.
- The src/ directory is supported by Next.js for application code. Keep project configuration files and public/ at the repository root.
- Do not rename framework-required files just to make their names more descriptive. Make the containing folder descriptive and keep the framework entry point thin.

UI STYLING AND FILE SIZE STANDARD

- Prefer Material UI (MUI) components and their built-in styling before reaching for custom styling.
- Use Tailwind CSS v4 utilities for layout and straightforward styling where appropriate.
- Create standalone CSS files or custom CSS rules only when MUI and Tailwind cannot reasonably satisfy the requirement, or when a component needs scoped styles for a complex visual treatment.
- Keep every handwritten source file at 100 physical lines or fewer, including components, CSS, tests, and configuration. Count blank lines and comments. Generated files, dependency lockfiles, and vendored code are excluded.
- Warn at 80 lines. Before and after each meaningful code change, check line counts and report any changed file at or above 80 lines or over 100 lines.
- Refactor by cohesive responsibility before exceeding 100 lines. Never compress code just to meet the limit or split it into meaningless fragments.
- Existing oversized files are technical debt and should be refactored incrementally with behaviour-preserving tests and visual checks.
- An automated local/CI check should warn at 80 lines and fail above 100. Until implemented and verified, perform the check manually.

NAMING STANDARD

- Use lowercase kebab-case for ordinary source folders and filenames. The user-approved documentation-folder name `Project Documentation/` is an intentional exception.
- Use explicit product and domain terms: job-discovery, authentication, user-profile, user-account, cv-studio, and job-tracking.
- Do not use vague feature folder names such as jobs, profile, or account for the target feature architecture.
- Keep public URLs and API contracts stable during folder-only changes.
- Use names that state the responsibility, such as job-listing-schema.ts, get-job-listings.ts, and update-job-listing-state.ts.
- Avoid vague filenames such as helpers.ts, utils.ts, common.ts, data.ts, manager.ts, and service.ts unless their meaning is unambiguous from a tightly scoped directory.
- Framework filenames such as page.tsx and route.ts are deliberate exceptions. Their parent route folders and the code they call must make the responsibility clear.
- Do not create empty folders simply to match this diagram. Create a folder when code for that responsibility exists or is being moved into it.
- The target structure below is proposed. Existing source and tests are not all organised this way yet.

TEST ORGANISATION AND FILE NAMES

The target is to separate test files from production source. The existing repository still has tests colocated with source, so this is a planned migration, not a completed change.

- Unit-test filenames should identify the behaviour or module under test, for example job-listing-schema.unit.test.ts or profile-form.unit.test.tsx.
- Integration-test filenames should identify the endpoint or interaction being verified, for example get-job-listings.integration.test.ts or update-job-listing-state.integration.test.ts.
- End-to-end test filenames should describe a complete user journey, for example search-job-listings.spec.ts or sign-in.spec.ts. Playwright's .spec.ts convention is retained.
- Do not name all API tests route.test.ts after moving them. The framework requires route.ts for the handler; it does not require that generic name for test files.
- Keep test configuration and setup in src/test/ only when it is configuration/support code. Actual tests belong under tests/.
- Before moving tests, inspect vitest and Playwright configuration, import aliases, mocks, setup files, test discovery patterns, and CI commands. Update configuration in the same change as the move.
- Classify tests by what they actually verify, not only by the source folder they currently occupy. A Route Handler test that verifies request validation, identity, access control, and persistence together belongs in integration-tests; an isolated schema or pure function test belongs in unit-tests.
- Do not claim the target tests structure exists until the files and configuration have been migrated and the test commands pass.

- Current API tests are named route.test.ts beside their Route Handlers. Current module tests are colocated under src/lib/jobs/, src/lib/profile/, and src/components/profile/. They have not been moved into tests/ yet.

- No account settings API, CV Studio API, or full Job Tracking application-record API is currently present in the inspected source tree.

- The proposed (job-listings), (user-profile), and (job-ingestion) API route groups are organisational examples. Before implementing them, verify route uniqueness and the resulting route table/build.
- Do not create empty target folders before the corresponding code or tests are ready to move.

MIGRATION CHECKLIST

1. Review the current source, tests, and import graph before each move.
2. Preserve every existing public page URL and API endpoint method/path/response contract during structural-only changes.
3. Move one coherent feature or test category at a time.
4. Update imports, test-runner configuration, Playwright testDir, and CI commands in the same change when affected.
5. Run the relevant Vitest tests, ESLint, and production build when the environment supports them; run Playwright tests where configured.
6. Record exactly which checks ran and their results. A successful documentation edit or GitHub commit is not proof that the application builds.
