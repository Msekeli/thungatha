Thungatha — Folder Naming Standard and Target Structure
Status: Naming principles confirmed; physical migration is incremental
Last updated: 18 October 2026
Branch: dev

PURPOSE
This file describes the intended, easy-to-navigate structure. It does not claim that every target path exists today. The verified current tree remains available from the repository tree on dev.

NAMING RULES
- Use descriptive lowercase kebab-case names for feature-owned folders.
- Preferred feature names: job-discovery, authentication, user-profile, user-account, cv-studio, and job-tracking.
- Job Discovery owns job-listing catalogue data, search, filters, source provenance, and per-user discovery state. Do not create a separate top-level job-listings feature unless a future, evidenced boundary requires one.
- Do not introduce vague feature containers such as jobs, profile, or account in the target structure.
- Technical/framework boundaries such as app, api, components, lib, and ui may remain where they express an established technical role; their feature-owned children should still be explicit.
- Next.js App Router folders normally define URLs. Use route groups in parentheses to make the filesystem responsibility explicit without changing the URL. Example: app/(user-profile)/profile/page.tsx still serves /profile.
- Existing URLs and API contracts are stable interfaces. Do not rename URL segments just to improve folder names. If a URL change is required, handle it as a separate, explicit product/API decision with redirects and consumer migration where appropriate.
- Do not create empty folders or placeholder files to match the target tree.
- Inspect all imports, route consumers, tests, auth/ownership checks, and data effects before each move. Verify each coherent migration before proceeding.

DOCUMENT AUTHORITY
- docs/ARCHITECTURE.md defines architectural boundaries.
- docs/FOLDER-NAMING-AND-API-ROUTE-MAP.md defines folder naming, route-group examples, the inspected API inventory, and known discrepancies.
- DECISIONS.md records the approved naming principle and migration constraints.
- This file is the navigational target map; it must be updated as migrations are completed.

CURRENT IMPLEMENTATION NOTES
- The existing discovery UI files currently live in src/thungatha-features/jobs/ui/. The target is src/thungatha-features/job-discovery/ui/; the rename is not implemented yet.
- Job provider adapters, ingestion, schema, and search currently live in src/lib/jobs/. They have not been moved into the Job Discovery feature.
- Authentication-owned UI currently lives in src/components/auth/.
- Professional Profile UI currently lives in src/components/profile/, while profile persistence/schema logic lives in src/lib/profile/.
- Existing API Route Handlers contain some query, validation, and persistence orchestration. Do not move them or rename API URLs blindly; extract services only where tests and boundaries justify it.
- Do not move files merely to populate every target directory. This target tree should evolve as code is actually migrated.
